## M3-SQL-01 — proposed catalogue type lookup / Services & Actions / Master Packages model (M3-T01)

**Definition.** The admin UI has one Individual items list with a Service/Action type filter, a Bundles tab, and a separate Master Packages page. One `catalogue` table holds both Service and Action rows. Create `catalogue_types` as a system-owned lookup, and require `catalogue.catalogue_type_id` to reference it; there is no PostgreSQL enum and no separate service or action table. Add these proposed `public` tables with created/updated timestamps and appropriate checks. Catalogue, bundle, package and promotion IDs are UUIDs; `catalogue_types.id` and its FK are SMALLINT, while auth-user FKs are text:

- `catalogue_types(id SMALLINT PK, code text UNIQUE NOT NULL, label text UNIQUE NOT NULL, created_at, updated_at)`; insert exactly `(1, service, Service)` and `(2, action, Action)` as required production reference rows in the same migration. `catalogue(id UUID PK, catalogue_type_id SMALLINT NOT NULL FK → catalogue_types.id ON DELETE RESTRICT, name, description, active)`.
- `bundle(id PK, name, description, active)`; `bundle_catalogue(bundle_id FK → bundle.id, catalogue_id FK → catalogue.id, PK(bundle_id, catalogue_id))`.
- `master_package(id PK, name, description, duration_minutes, base_price, published, active)`; `package_catalogue(package_id FK → master_package.id, catalogue_id FK → catalogue.id, PK(package_id, catalogue_id))`; `package_bundle(package_id FK → master_package.id, bundle_id FK → bundle.id, PK(package_id, bundle_id))`.
- `promotion(id PK, title, description, discount_type, discount_value, starts_on date, ends_on date, published, active)`; `promotion_package(promotion_id FK → promotion.id, package_id FK → master_package.id, PK(promotion_id, package_id))`. Title/description and inclusive date fields match the admin Promotion form. This join records package applicability only; it neither changes nor stores a discounted package price.
- The FK rejects unknown type IDs; unique code/label values reject duplicate type definitions. Only controlled migrations may add or change type rows: the current UI and business rules support exactly Service and Action, and M3 has no admin type-management command. CHECK constraints require positive duration, nonnegative price, valid discount type/value, `starts_on <= ends_on`, and nonempty catalogue/package/promotion titles. Composite PKs reject duplicate join rows. Deactivate/retire referenced service/action, bundle, package and promotion records instead of cascading away booked facts. Expansion uses unique Service/Action IDs across direct and bundled membership; later business code must revalidate eligibility and calculate the booking final_price on the server.

**Purpose.** Let `catalogue` reference a controlled type definition while mapping the UI faithfully: one typed Service/Action record, reusable bundles of those records, and packages composed of individual records and/or bundles. Give admin future-selection CRUD and public package/promotion reads a durable common model, including package-specific time-bound discounts and no duplicate item expansion.

**Responsibilities and boundaries.** `catalogue_types` owns the stable Service/Action IDs, codes and labels; `catalogue` owns each item identity and its required type reference; the join tables own bundle/direct-package membership. The model also owns current package price and promotion applicability constraints. The two type rows are required production reference data, not sample catalogue data. This migration does not own booking snapshots, historical prices, public content/media publication, or a test seed. A promotion's active/published flags, inclusive date range and package membership govern automatic eligibility on the booking creation date in Asia/Jakarta; they do not alter `master_package.base_price` or rewrite existing bookings. T02 owns transactional create/edit validation that rejects every same-package inclusive date overlap, including concurrent commands: lock the affected `master_package` rows in stable ID order, then query existing `promotion_package` links and date ranges before writing the promotion and all links in the same transaction. Promotion edits that change package membership use the same lock and check. No extra price or overlap table is proposed. T02/T03 activate the model and T04 references its stable IDs.

**Relationships/cardinalities.** One `catalogue_types` row classifies zero-to-many `catalogue` rows, and every catalogue row has exactly one type. One bundle has zero-to-many `bundle_catalogue` rows, each joins one typed service/action item; one package has zero-to-many direct item and bundle membership rows; one promotion applies to zero-to-many packages via `promotion_package`; each join row belongs to exactly one parent on each side. The SVG labels PK/FK and the `1 : 0..N` edges.

## M3-SQL-04 — proposed booking aggregate (M3-T04)

**Definition.** After SQL-01, add `booking(id UUID PK, customer_id text FK → auth.user.id, package_id UUID FK → master_package.id, promotion_id UUID nullable FK → promotion.id, wedding_date date, wedding_location text, status text, package_snapshot jsonb, promotion_snapshot jsonb nullable, final_price numeric, created_at, updated_at)`. Use a CHECK over the Project Context's canonical core and M4 exception status labels, with M3 commands limited to the three core states. Add `booking_status_history(id UUID PK, booking_id UUID FK → booking.id, actor_id text FK → auth.user.id, from_status nullable, to_status, occurred_at)` and ordered index `(booking_id, occurred_at, id)`. Initial booking plus `Menunggu Konfirmasi` history entry are atomic. The package snapshot holds the base price, name, duration, description and expanded composition at submission. The server uses the same trusted transaction timestamp for `booking.created_at` and eligibility. Its Asia/Jakarta calendar date must fall within `promotion.starts_on` through `ends_on`, inclusive; the promotion must be active, published and linked to `booking.package_id`. The unique matching promotion applies automatically without a client-supplied promotion ID. Its snapshot records title, type, value and applied discount; if none matches, `promotion_id` and `promotion_snapshot` are null. `final_price` is the actual price committed for that booking after the discount, or the base price when no promotion is applied. The server computes these facts at submission; package and promotion edits never recalculate them. No separate `booking.created_date` column is needed because the business date is derived from its persisted `created_at` in Asia/Jakarta. Enforce nonnegative final price, required package snapshot structure, and snapshot immutability after insert (database trigger or equally strong schema-backed mechanism to be detailed in the confirmed migration). History is append-only by permissions/trigger and never cascade-deleted by routine service/package changes. Delete policy for customer/bookings is outside M3; do not cascade user deletion into booking history.

**Purpose.** Preserve one shared record and historical terms while allowing the admin to change current services, actions, bundles and packages for later bookings.

**Responsibilities and boundaries.** Own booking identity, customer relationship, submission facts, official current status and ordered status changes. It does not own proof bytes, proof audit, cancellation/reschedule data, WhatsApp state or date closure. Package/promotion FKs identify source records; the optional promotion FK identifies an applied promotion, not merely one that was active. Snapshots and `final_price`, not live joins, supply historic display. T05/T06 activate customer/admin paths.

**Relationships/cardinalities.** One auth user owns zero-to-many bookings; one package is selected by zero-to-many bookings; a booking has zero or one promotion; one booking has one-to-many status history rows after creation; each history row has one actor user. The SVG labels all FK fields and cardinalities.

## M3-SQL-07 — proposed date protection (M3-T07)

**Definition.** After SQL-04, add `admin_closed_date(date date PK, closed_by text FK → auth.user.id, created_at timestamptz)`. Add a partial unique index on `booking(wedding_date)` where `status = 'Booking Berhasil'`. Customer submission, admin successful transition and admin closure/open must use one transaction-level date lock/conflict decision so a closure and success cannot both commit for the same date. The partial unique index independently rejects two successful bookings on a date. An open command removes only an admin closure; it does not change a successful booking. Pending statuses do not enter the partial index and never reserve the date. The lock/decision is runtime logic bound to these tables and is required by T07, not a test-only migration branch.

**Purpose.** Make date availability authoritative across customer/admin surfaces under concurrency, while preserving the confirmed rule that only deliberate admin closure or `Booking Berhasil` blocks selection.

**Responsibilities and boundaries.** Own admin closure identity/date and database protection against duplicate successful bookings. The transaction owns cross-table closure/success conflict ordering. Customer reads project only date/unavailable facts; they never expose booking/customer identity. M4 reschedule/cancellation must consume this invariant when releasing or moving a reservation; M3 does not implement those exceptions.

**Relationships/cardinalities.** One admin user can close zero-to-many dates; each closed date has exactly one closing admin. The date conflict between `admin_closed_date.date` and successful `booking.wedding_date` is an exclusion invariant, shown as a dashed relation in the SVG, not a FK.
