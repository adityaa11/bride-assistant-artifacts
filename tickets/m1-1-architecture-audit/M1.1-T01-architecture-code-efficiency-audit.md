## Outcome

Produce a reproducible, versioned audit of the active M1 application and its direct test/build paths. Its finding register distinguishes verified inefficiency or maintainability risk from hypothesis, preserves accepted boundaries, and gives W02 enough evidence to decide bounded refactor tickets or a no-refactor exit. The ticket owns the audit and its evidence only.

## Exact scope

Inspect public, customer and admin route composition; shared scenario/adapters; fixture media and `DocumentStore` ownership; components, CSS and static assets; direct test/build paths; and the M2 replacement seams those paths expose. Trace actual callers and consumers. Assess unnecessary work, semantic duplication, rendering/data-flow cost, client-boundary cost, ownership complexity and stale web patterns. Measure a focused baseline with repeatable settings before claiming an efficiency defect. Record non-findings where a plausible lead is rejected.

Run the bundled modern-web `legacy-scan . --json`; inspect relevant pinned guides, Next.js 16.4.6 local documentation and project browser/CSP constraints before recommending Next.js or browser changes. The scan is one input, not the audit's whole scope. Reconcile prototype-only source matches and false positives against active code. Where a candidate touches UI composition, responsive behavior, interaction or accessibility, assess it against the established M1 reference and visual contract, including the source-led admin frame rule.

## Entrypoint

The GO audit owner starts from the exact source commit and accepted M1/H-17 evidence. Inputs are Git-tracked `app/`, `shared/`, `public/`, `tests/`, `scripts/`, configuration and direct reference evidence, plus read-only route observations. Source and fixtures are review inputs, not trusted business authority. A missing/mismatched commit, unavailable route, failed probe or ambiguous accepted boundary is recorded as a limitation or unresolved finding; it is never silently treated as a passed observation. The owner does not modify application code or fixture data.

## Endpoint

One versioned Markdown register plus indexed, reproducible evidence in the validated artifact repository, bound to the exact code commit. It contains stable finding IDs, verified/hypothesis classification, route/module and actual use path, baseline observation or measured result, impact, authority, bounded candidate, likely regression and one permitted disposition. It also records non-findings, measurement conditions/limits, preserved contracts, and unresolved questions. A complete no-action result is valid if supported by the observations. CK review of the audit checkpoint, not the audit author, decides whether T01 passes.

## Reuse and centralization decision

`RD-1.1-01`: `getScenario(scenarioId: ScenarioId | string): ScenarioResult` in `shared/scenarios/adapter.ts` is the existing versioned read boundary for multiple routes. Compare its error result and actual consumers before suggesting shared changes; no raw `scenarioCatalogue` import in features. `RD-1.1-02`: `AdminWorkspaceFrame` owns admin shell props and layout; content-specific composition stays with each admin workspace. `RD-1.1-03`: `DocumentStore` has byte put/read/remove semantics while the local content store has collection association and replacement semantics; keep those ownership and failure boundaries distinct. An additional repeated-capability candidate gets its own `ReuseDecision` in the register with evidence, owner, current/planned consumers, semantic/error/lifecycle comparison and `reuse-existing`, `extract-shared`, `keep-local` or `planning-required`. A shared extraction is not authorized by this audit.
