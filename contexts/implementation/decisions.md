## Deferred and blocked decisions

### D-01 Vercel application and DocumentStore platform

**Status:** `superseded` by D-06 · **Historical decision:** Vercel hosts the Next.js application and Vercel Private Blob backs the production `DocumentStore`.  
**Reason for replacement:** User selected Neon Object Storage as the production S3-compatible byte authority alongside Neon PostgreSQL (19 Nov 2026). Vercel remains the application host. **Affects:** historical M2-R01/M2-W01, M4-W01, M5-W03/04. **Revisit trigger:** Restore only if D-06 is superseded by an explicit provider decision.

### D-05 Production PostgreSQL provider and location

**Status:** `confirmed` · **Decision:** Neon PostgreSQL 18.7 in Singapore (`ap-southeast-1`) is the production system of record; Vercel runs the application in Singapore (`sin1`).  
**Rationale:** Neon preserves the confirmed PostgreSQL 18.7 baseline and gives Vercel-native serverless/preview branch support. Supabase was not selected because its managed major/version path conflicts with PostgreSQL 18.7 and its Auth/Storage services would duplicate Better Auth. **Implementation constraint:** use Neon as the PostgreSQL authority; retain Better Auth as the identity authority. Record the provisioned endpoint, connection configuration, and final backup/PITR terms before real data. **Affects:** M2-R01/M2-W01 and M5-W03. **Revisit trigger:** Neon plan lacks required recovery terms, regional availability changes, or the PostgreSQL major changes.

### D-06 Production DocumentStore provider and location

**Status:** `confirmed` · **Decision:** Neon Object Storage in the same selected Singapore Neon project backs production `DocumentStore` for every uploaded media/proof byte; Vercel hosts the Next.js application only. Docker provides local PostgreSQL and a disposable local `DocumentStore` adapter for development; T18's ignored local fixture adapter follows the same byte boundary.
**Evidence:** User direction on 22 Nov 2026 establishes one upload-byte boundary; Neon Object Storage is S3-compatible, supports private buckets, and supports short-lived presigned URLs for private reads and direct uploads. **Boundary:** Neon credentials are server-only; the application authorizes the booking owner/admin before minting a URL. The development/fixture adapter is not production storage and must not receive real customer or payment-proof media. Portfolio, testimonial and event record association/replace/remove lives above `DocumentStore`; it cannot become a separate byte store. **Affects:** M1-W07/T18, M2-W04, M4-W01/W05/W06, M5-W03/04. **Enables:** one Neon authority for production relational facts and uploaded bytes without storing bytes in PostgreSQL. **Revisit trigger:** lack of Singapore availability for the provisioned account, unacceptable recovery/data-transfer terms, or a change to sensitive-byte handling.

### D-02 Runtime and auth/data integration

**Status:** `confirmed` · **Question:** Which current Next.js, Better Auth, PostgreSQL driver/ORM, and Better Auth adapter versions are compatible after D-01?  
**Approved starting baseline (user confirmed, 19 Nov 2026; `@types/node` correction approved 24 Nov 2026):** Node `24.22.3`; Next.js `16.4.6`; React/React DOM `19.3.1`; TypeScript `5.9.3`; Better Auth `1.7.26`; Zod `4.6.7`; `pg` `8.23.1`; `@types/node` `24.6.2`; PostgreSQL `18.7`. The original `@types/node` entry was `24.6.6`, which npm does not publish; `24.6.2` is the existing exact lock version and the final `24.6.x` release. The user approved that exact correction after a package advisory and Vercel/Neon compatibility review. PostgreSQL 18 is currently supported through November 2030; the selected managed provider must offer it. Next 16 requires Node 20.9+ and accepts React 19; Better Auth 1.7.26 declares compatibility with Next 16, React 19, and `pg` 8. Node 24 is both Active LTS and Vercel-supported. Node 26 is deliberately excluded from this baseline. TypeScript 5.9 is retained rather than the TypeScript 6/7 transition line until a later, explicit review.
**Affects:** M2-R02 and all backend packages. **Enables:** dependency lock and persistent auth. **Verification prerequisite:** create the exact lockfile, install cleanly, and pass build/type/test checks before deployment. **Revisit trigger:** provider incompatibility, peer-dependency conflict, or a security advisory; update patches within these approved majors and rerun the same evidence.

**Security/defect recheck (19 Nov 2026):** Node 24.22.3 is the current patched security release. Next 16 is Active LTS and 16.4.6 is beyond the listed critical-advisory patched floors, but an open 16.4.6 Route Handler defect drops explicitly supplied `Content-Length`; it can break download progress and PDF range retrieval. **Confirmed delivery choice:** after server-side ownership/admin authorization, issue a short-lived direct Neon Object Storage URL rather than proxying private document bytes through a Next Route Handler. M4 must regression-test authorized PDF download and range behavior; if range semantics fail, defer range support rather than adding a route-handler proxy. React 19.3.1 is current; the prior React Server Components critical issue predates this baseline. Better Auth 1.7.26 is above the known fixed floors cited in its late-2026 security advisories; do not enable Magic Link/OAuth/Expo/SSO features without a fresh advisory check and configuration-specific test. Zod 4.6.7 has no listed open direct advisory, but follows a repository credential incident whose malicious commits were not published to npm; use lockfile integrity/provenance controls. No direct advisory was found for `pg` 8.23.1 or TypeScript 5.9.3; keep database TLS certificate verification enabled and use parameterized queries. PostgreSQL 18.7 includes the November security fixes; for an existing 18.x database, follow its release notes on extension rebuilds, affected indexes, and incremental-backup replacement. `documented`, medium-high confidence.

### D-03 Sensitive document policy

**Status:** confirmed technical requirements; five production decisions pending. [PA-M2-T07-01 approved](decisions/PA-M2-T07-01-approved.md) separates T07 technical capability from production policy approval, operational readiness and activation authority. T07 CK can approve a shared technical foundation with explicit pending decisions; it cannot approve production deletion or upload activation.

**Authoritative retention and proof design (user intent, 20 and 24 Nov 2026):** accept JPEG, PNG or PDF, at most 10 MiB each and three files per payment request. Eligible operational proof is retained eight calendar months from final proof review, or upload if never reviewed. Any record professionally determined to be subject to the applicable Indonesian ten-year statutory requirement retains at least ten years under an approved classification/start rule. Whether proof bytes or proof audit records are in that class remains an accountant/legal determination. Unknown classification, missing approval or active hold cannot authorize production deletion. A five-minute profile is only a disposable verification setting; controlled-clock tests must also exercise actual eight-month and ten-year policy durations and start events. At eligible expiry, remove bytes and proof-specific metadata/audit while preserving the booking's own status history. Proof audit events remain append-only during their applicable retention period and contain no file contents, names, signed URLs or credentials.

**Confirmed technical policy:** booking owner uploads only while `Menunggu Pembayaran`; admin does not upload. Validate extension, detected type/signature, size, generated opaque key, authentication and authorization. Review alone never changes booking status. Private proof access requires authorization. Scanner infected, unavailable and timeout outcomes fail closed and quarantine; an active accountable hold prevents deletion in every environment. Incident handling immediately contains access, preserves required audit evidence and evaluates the statutory 3 × 24-hour notification requirement. Review policy every 12 months and after incident/provider change. Explicit per-item permission is required before testimonial/portfolio media becomes public.

**Policy/configuration separation:** versioned policy authority contains requirements and accountable approvals/evidence; environment profiles contain runtime values and adapter choices; validation binds them to trusted deployment identity; shared domain logic consumes validated configuration and ports, not legal documents or environment-name branches. Production rejects development durations, controlled clocks, disposable adapters and missing decisions. Development/test reject production databases, object stores, credentials and real customer data. Unknown combinations fail closed. T07 implements this only for the proof-policy foundation; M4/M5 integrate actual providers and release gates.

**Five deferred production decisions, unchanged:** (1) PDP processing basis, final notice and data-subject request contact; (2) scanner provider, terms and cost; (3) accountable legal/business hold criteria and release authority; (4) Neon account-backed database/object RPO/RTO, backup terms and restore ownership; (5) accountant/legal determination of ten-year applicability to proof bytes/audit. Record each approved value, owner, date and evidence. M4-W07 owns PDP, scanner, hold and statutory policy/control evidence; M5-W03 owns recovery evidence; M5-W05 checks all before activation. T01's six-hour PITR/manual snapshot evidence was accepted for preparation only. No scanner, legal conclusion, hold criterion, recovery target or production activation is selected here.

**Affects:** M2-R03/T07, M4-W01/W02/W07, M5-W03/W05. **Enables:** development of the shared proof capability and later M4 integration without waiving the five production gates. **Revisit trigger:** before production proof activation or a material policy/provider change.
