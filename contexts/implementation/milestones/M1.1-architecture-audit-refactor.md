# M1.1 — Architecture audit and bounded refactor

**Source code repository / planning baseline:** `https://github.com/adityaa11/bride-assistant.git` at `79b3478995737dd73165afaba50369dcb5242a08`.

**Status:** `planned` · **Advances:** evidence-backed maintainability, efficient implementation, and a safer fixture-to-backend handoff.
**Outcome:** The M1 application and its relevant contracts have an architecture and code-efficiency audit, a versioned finding register, and bounded, verified refactors for findings accepted into M1.1. The audit result is the source for a later M1.1 ticket set; it is not itself a ticket set or permission to change code.

**Entry:** M1-T17/H-17 CK `PASS` at the bound code checkpoint; M1's fixture/UI exit evidence remains the baseline. The formal M1 status update is separate from this planning addition. **Excludes:** new product behavior, real authentication, production persistence or media, provider changes, visual redesign, and M2–M4 backend work. **Handoff:** an audited, reviewable fixture application and explicit residual findings/seams to M2. **Risk:** treating style preferences or a scanner suggestion as a defect; contain through observed use paths, measured impact, and the accepted M1 contracts.

## Audit contract

Inspect the active application and its direct test/build paths across public, customer, admin, shared scenario/adapters, fixture media, and component/style boundaries. Look for unnecessary work, duplication with identical semantics, costly rendering or data flow, excessive client-side code, weak module or ownership boundaries, avoidable complexity, stale or unsupported web patterns, and gaps that make the M2 replacement seams harder to maintain. Include a focused performance measurement when claiming inefficiency; record environment, baseline, and repeatable comparison. A static warning alone is a lead, not proof.

Use `modern-web-guidance` as one browser-platform lens: run its bundled `legacy-scan`, inspect the relevant bundled guides, and verify applicability against this repository's supported browsers, Next.js version, visual contract, and CSP. The audit is broader than the legacy scan. Read the relevant guide in `node_modules/next/dist/docs/` before proposing or writing Next.js code, per `AGENTS.md`. Use `frontend-awareness` only when a candidate touches UI composition, responsive behavior, interaction, or accessibility. Do not silently change a visually matched M1 reference surface.

The finding register must give each candidate a stable ID, affected route/module and actual use path, observed behavior, evidence or measurement, impact, accepted boundary, proposed bounded change, likely regression, and disposition: `M1.1-refactor`, `defer-to-named-successor`, `no-action`, or `unresolved`. Distinguish a verified inefficiency from a hypothesis. Check whether each candidate would alter a confirmed Project/Stack/Implementation decision, M1 fixture authority, privacy/publication boundary, or M1 reference contract. Escalate such a conflict through planning before ticket creation.

**Exit gate:** every in-scope finding has a supported disposition; each accepted M1.1 refactor has a bounded reviewed ticket and current regression evidence; claimed efficiency gains have comparable measurements; unchanged behavior retains the M1 route, scenario, visual, accessibility, security, and media boundaries. If the audit finds no justified change, an explicit no-refactor record satisfies the conditional refactor branch. Any unresolved finding that affects M2's accepted seams blocks M1.1 exit until resolved or deliberately routed to a named successor. A failed gate returns to W01/W02 or the affected ticket; it does not silently advance M2.
